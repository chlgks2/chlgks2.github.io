① 모델과 툴을 비교해서 골랐습니다

쓸 수 있는 것을 쓴 게 아니라, 기준을 세우고 비교한 뒤 고른 기록입니다.

기준부터 만들었습니다

PixG에서 「픽셀 느낌의 이미지」를 목표로 두면 언제 끝났다고 할지 알 수 없었습니다. 그래서 게임 엔진이 실제로 읽을 수 있는가를 기준으로 조건 4개를 먼저 못박았습니다.

기준이 있어야 비교가 성립합니다. 조건을 못박은 뒤에야 어떤 기술이 필요한지, 경쟁 서비스와 무엇이 다른지가 보였습니다.

Blind Dating에서는 17종을 돌려보고 골랐습니다

항목비교와 결정
체크포인트 13종 (약 59GB) 비교 → 운영 dreamshaperXL_lightningDPMSDE
Juggernaut-XL v9가 정체성 유지에 유리했지만 생성 시간이 길어 저스텝 계열로 교체했습니다
스타일 LoRA 지브리 4종 A/B 비교 → giblylast 채택
Ghibli_xl_v2는 스타일이 강하나 얼굴 왜곡, ghibli_style_offset은 변환 강도 부족
정체성 유지 IP-Adapter FaceID Plus V2 (SDXL) + InsightFace buffalo_l
얼굴 복원 face_yolov8m + SAM vit_b · 업스케일 4x-UltraSharp

가중치 총합 약 69GB는 저장소에 넣지 않고 models/manifest.json + 다운로드 스크립트로 환경을 재구성할 수 있게 했습니다.

② 생성 파이프라인을 설계했습니다

모델 하나를 호출한 게 아니라, 여러 단계를 이어 붙여 하나의 결과물이 나오게 만든 작업입니다.

Blind Dating — ComfyUI 5단계

파라미터마다 이유가 있습니다

결정근거
txt2img 대신 img2img
denoise 0.6		 txt2img는 원본의 구도·포즈가 사라져 「내 사진」이라는 느낌이 없어집니다. 구도는 유지하고 화풍만 바꾸려고 부분 디노이즈를 선택했습니다
IPAdapter와 LoRA weight를 분리 튜닝 정체성(IPAdapter)과 스타일(LoRA)이 같은 샘플링에서 서로 상쇄됩니다. 스타일마다 균형점이 달라 개별 조정했습니다
FaceDetailer 추가
denoise 0.3		 전신 사진은 얼굴에 할당되는 latent 해상도가 부족해 눈·입이 뭉개집니다. 얼굴만 잘라 재생성한 뒤 SAM 마스크로 합성하고, 인물이 바뀌지 않도록 denoise를 억제했습니다
업스케일을 ×1.2 / denoise 0.15로 제한 업스케일의 디노이즈는 사실상 재생성이라 얼굴 인상이 변합니다. 역할을 「디테일 보정」으로 한정했습니다
IPAdapter provider CPU → CUDA InsightFace 임베딩 추출이 병목이었습니다

PixG — 생성부터 게임 에셋까지

구간설정
베이스Stable Diffusion 1.5 + 픽셀아트 LoRA · CLIP skip -2
동작 생성AnimateDiff animatediffMotion_v15V2 · context_length 16 · steps 20 / cfg 8
자세 제어ControlNet 2종 — OpenPose 1.0 + Depth 0.2
환경개인 RTX 3060 6GB / 아카데미 RTX 4090 24GB

OpenPose를 1.0으로 강하게 걸어 동작을 확정하고, Depth는 0.2로 약하게만 얹어 입체감만 보조하도록 역할을 나눴습니다. Depth를 올리면 픽셀아트 특유의 납작한 화풍이 무너집니다.

「픽셀 느낌의 이미지」와 「게임에 넣을 수 있는 에셋」 사이에 이 구간이 있습니다. 경쟁 서비스가 요구조건 2개에서 멈춘 이유도 여기였습니다.

③ 생성 워크플로우를 자동화했습니다

GPU 서버가 작업을 가져가는 구조로 뒤집었습니다

GPU 예산이 없어 사설망 개인 머신을 써야 했습니다. 인바운드 포트를 열 수 없어, 서버가 GPU를 호출하는 대신 GPU 워커가 백엔드를 폴링해 작업을 선점하는 방향으로 바꿨습니다.

구성내용
작업 큐 AIJob 테이블을 큐로 설계 — FIFO · 상태 머신 · 실패 사유 전달
워커 백엔드 폴링 → 작업 선점 → ComfyUI HTTP 호출 → 결과 전송 · 타임아웃과 예외 처리
헬스체크 FastAPI /health — 워커 스레드와 ComfyUI 연결을 동시에 확인
대기 흡수 생성 시간을 줄일 수 없다고 판단하고, 설문 21문항을 대기 구간에 겹쳐 배치해 체감 대기를 사실상 0으로 만들었습니다

Celery를 일부러 쓰지 않았습니다. DB 테이블 하나로 FIFO·상태 머신·실패 사유 전달이 충족되는지 확인한 뒤, 5주 일정에서는 브로커 운영 비용이 더 크다고 판단했습니다. 대가(원자적 선점 부재)와 개선 방향도 함께 문서로 남겼습니다.

PixG는 후처리 전 구간을 스크립트로 묶었습니다

생성된 프레임을 사람이 손대지 않고 게임 엔진이 바로 읽는 에셋으로 바꾸는 구간입니다. 배경 제거 · 화질 복원 · 규격 통일 · 격자 배치가 한 번에 돕니다.

결과물

프롬프트 한 줄에서 스프라이트 시트까지

프롬프트 입력 → 생성 → 다운로드까지의 실제 화면. yellow hair, blue shirts, blue pants 한 줄을 넣으면 달리기 사이클 스프라이트 시트가 배경까지 처리된 상태로 나옵니다.

생성 결과 갤러리 — 프롬프트와 결과물이 함께 보관됩니다.

실제로 쓰이는지 확인했습니다

「이미지가 잘 나왔다」는 자체 평가로 끝내지 않고 실제 사용처에 넣어봤습니다. 요구조건 4개를 정의한 이유도 여기에 있습니다 — 하나라도 빠지면 ZEP에 올라가지 않습니다.

Blind Dating은 실사용 서비스에 들어갔습니다

해보지 않은 것

직무 요건과 대조해 솔직하게 적었습니다.

항목현재 상태
Veo · Kling 등 상용 영상 생성 모델 써본 적 없습니다. 영상 생성은 AnimateDiff로 프레임 시퀀스를 만드는 방식까지 경험했습니다. 다만 모델을 비교·검증해 고르는 방식은 위 13종·4종 비교와 같습니다
에이전트화 경험 없습니다. 워크플로우 자동화(작업 큐 · 폴링 워커 · 상태 머신)까지이며, LLM이 도구를 선택해 실행하는 구조는 만들어보지 않았습니다
크리에이터 협업 콘텐츠 제작 실무 협업 경험은 없습니다. 팀 프로젝트에서 기획·디자인 담당과 요구조건을 맞춰 생성 결과를 조정한 경험까지입니다
이미지 생성 모델 파인튜닝 이미지 생성 모델은 전부 공개 사전학습 모델이며 파인튜닝하지 않았습니다. 다만 텍스트 분류 모델은 직접 학습했습니다 (Emour — KcELECTRA 파인튜닝)
영어 OPIc IM1. 기술 문서 독해는 가능하나 회화는 부족합니다
해보지 않은 것을 적는 이유 — 이 포트폴리오의 모든 수치는 코드·로그·체크포인트에서 직접 확인한 실측값입니다. 확인되지 않는 것은 적지 않았고, 해보지 않은 것은 해보지 않았다고 적었습니다.
