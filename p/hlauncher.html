무엇을 만들었나

StarCraft 온라인 플레이에는 두 가지 불편이 있습니다. 하나는 핵 사용자, 다른 하나는 고의로 게임을 멈추게 만드는 유저입니다. 기존에 쓰이던 런처가 단종되면서 대응 수단이 사라졌고, 그래서 직접 만들었습니다.

기능내용
핵 탐지 런처 Battle.net / StarCraft 프로세스를 감시하다가 게임이 실행되면 탐지 엔진을 붙입니다. 설치 경로는 레지스트리에서 자동으로 찾습니다
대기방 참가자 조회 같은 방에 누가 있는지 배틀태그 단위로 보여줍니다 — 화면에 표시되지 않는 정보입니다
블랙리스트 · 화이트리스트 다시 만나고 싶지 않은 유저를 표시해 두면 방에 들어왔을 때 알려줍니다. 자주 하는 사람은 즐겨찾기로 구분합니다
최근 플레이 기록 같이 했던 사람을 자동으로 쌓아 둡니다
무한디스 대응 고의로 게임을 멈추게 만드는 상황을 감지합니다. 아래 상세 →

구조

hlauncher.exe (Go)
  ├─ ui        WebView2 웹 인터페이스 (HTML/CSS/JS ↔ Go 바인딩)
  ├─ app       오케스트레이션 — 상태 관리 · 이벤트 중계
  ├─ monitor   프로세스/모듈 감시 (Toolhelp32)
  ├─ memscan   외부 프로세스 메모리 읽기
  ├─ lagwatch  게임 클럭 감시 · 멈춤 판정
  ├─ registry  설치 경로 자동 탐지 (HKLM Uninstall)
  ├─ loader    WinVerifyTrust 코드 서명 검증
  └─ config    %APPDATA% 설정 영속화

cmd/  hlauncher · hldiag · hlscan · hlmem · hllag · hllagsim · … (10개)

진단 도구를 따로 뒀습니다. GUI 없이 콘솔에서 게임 감지·경로 탐지·메모리 스캔을 각각 확인할 수 있습니다. hllagsim 은 실제 게임 없이 게임 클럭과 대기 타이머만 흉내 내 감시 로직을 검증하는 시뮬레이터입니다 — 매번 게임을 켜서 테스트할 수 없어 만들었습니다.

처음 다루는 언어·영역을 어떻게 감당했나

Go도, Windows 데스크톱도, Win32 API도 이 프로젝트에서 처음 다뤘습니다. AI와 대화하며 코드를 쓰는 방식(바이브 코딩)으로 진입 속도를 끌어올리고, 판단이 필요한 지점은 직접 파고드는 방식으로 진행했습니다.

"AI가 짜줬으니 내 실력이 아니다"라고 생각하지 않습니다. 무엇을 만들지 정하고, 돌아가지 않는 이유를 찾고, 두 방식 중 무엇을 택할지 판단하는 일은 그대로 남습니다. 오히려 모르는 영역에 손을 댈 수 있는 범위가 넓어졌습니다.

그래도 직접 판단해야 했던 것들

문제판단
32비트로 빌드하고 있었습니다 빌드 스크립트가 GOARCH=386 이었습니다. 원본이 32비트 자산을 다루기 때문인데, 정작 StarCraft: Remastered 는 x86_64 라 32비트 바이너리로는 게임 메모리를 읽을 수 없습니다. 깨진 바이너리가 나오고 있었고, amd64 로 바꿔 해결했습니다
스캔이 닿지 않는 영역이 있었습니다 기존 스캔은 MEM_PRIVATE(힙)만 봤는데, 필요한 엔진 전역 변수는 StarCraft.exe 이미지의 MEM_MAPPED 쓰기 영역에 있었습니다. 영역 필터를 고쳐 닿게 했습니다
실험판이 본체를 망가뜨렸습니다 복사해 만든 실험 빌드가 같은 뮤텍스·설정 폴더·파이프 이름을 써서 본체와 동시에 실행할 수 없었고 데이터도 섞였습니다. version.InstanceID() 하나가 세 이름을 전부 결정하도록 바꿔 설정·블랙리스트·기록이 완전히 분리되게 했습니다

이 셋 다 "코드를 짜는 문제"가 아니라 "무엇이 잘못됐는지 찾는 문제"였습니다. AI에게 물어서 나오는 답이 아니라, 증상을 재현하고 범위를 좁혀야 나오는 답이었습니다.

기술 선택 — 세 가지 중에 골랐습니다

대기방 참가자와 배틀태그를 가져오는 방법은 세 가지가 있었습니다.

방식내용채택
스크린샷 + OCR 화면을 찍어 글자를 인식. 화면에 안 보이는 값은 못 읽고 정확도도 떨어집니다 ✗
DLL 인젝션 게임 안에 코드를 넣어 내부에서 읽음. 정확하지만 안티치트가 핵으로 오인할 수 있고 크래시 위험도 있습니다 ✗
외부 메모리 읽기 게임이 RAM에 올려둔 데이터를 밖에서 복사해 읽음. 게임 프로세스를 건드리지 않습니다 ✓
가장 정확한 방법이 아니라, 가장 덜 위험한 방법을 골랐습니다. 인젝션이 더 쉽고 정확했지만 계정 정지·크래시 위험이 있습니다. 외부 읽기는 게임을 수정하지 않고 읽기만 하므로 그 위험이 훨씬 낮습니다.

읽기 파이프라인 — Windows API 4개

OpenProcess(PROCESS_VM_READ | PROCESS_QUERY_INFORMATION, pid)
        │  게임 프로세스를 "읽기 권한"으로 연다
        ▼
VirtualQueryEx(주소)  ── 반복 ──▶  메모리 영역 목록
        │  필터: MEM_COMMIT + 읽기가능 + 비가드 + ≤96MB
        ▼
ReadProcessMemory(base, size)
        │  선택한 영역을 1MB 청크로 우리 프로세스에 복사
        ▼
바이트 패턴 검색 · 구조체 파싱

게임은 서버에서 받은 데이터를 자기가 쓰려고 RAM에 복호화해 풀어놓습니다. 그 이미 복호화된 데이터를 옆에서 읽는 것이라, 네트워크 패킷을 직접 해독할 필요가 없습니다.

무한디스 대응 — 대기 시간만 줄입니다

StarCraft 멀티플레이는 락스텝(lockstep) 입니다. 모든 플레이어의 그 턴 입력이 도착해야 다음 턴을 계산합니다. 그래서 한 명이 패킷을 끊으면 그 사람만 멈추는 게 아니라 전원이 멈춥니다. 대역폭을 일부러 조여 게임 전체를 랙 걸리게 만드는 행위가 성립하는 이유입니다.

스타크래프트는 응답 없는 상대를 곧바로 버리지 않습니다. 일시적인 랙일 수 있으니 약 45초를 기다린 뒤 드랍합니다. 이 45초가 반복해서 악용됩니다.

H런처가 하는 일은 그 대기 시간을 줄이는 것뿐입니다. 드랍 자체는 여전히 스타크래프트가 자기 로직으로 수행합니다 — "언제 판단할지"만 앞당깁니다. 게임에 코드를 주입하지 않습니다.

감지는 엔진 전역 변수 두 개를 외부에서 읽기만 해서 이뤄집니다. 게임 클럭이 멈췄는지, 대기 타이머가 돌고 있는지를 보고 판단합니다. 폴링 주기와 클럭 보정값은 환경마다 달라 보정값을 측정해 저장하도록 했습니다.

실제 게임 없이 검증하려고 시뮬레이터(cmd/hllagsim) 를 따로 만들었습니다. 게임 클럭과 대기 타이머만 흉내 내면 감시 로직은 그대로 시험할 수 있습니다. 매번 사람을 모아 게임을 켤 수 없어서 내린 선택입니다.

한계와 기록

항목내용
개인용입니다 배포를 목적으로 만들지 않았습니다. 본인 PC에서 쓰려고 만든 도구입니다
원본 자산을 배포하지 않습니다 탐지 엔진과 인젝터는 원본 제품의 서명된 바이너리입니다. 빌드에는 쓰지만 저장소에서 제외했습니다 (.gitignore 에 명시). 제가 다시 쓴 것은 런처 셸(오케스트레이션 계층) 입니다
메모리 주소 의존 게임이 업데이트되면 전역 변수 위치가 바뀌어 스캔이 깨질 수 있습니다. 패턴 검색으로 완화했지만 근본적 한계입니다
환경 의존 폴링 주기·클럭 보정값이 PC마다 달라 보정 과정이 필요합니다
진행 중 완성된 제품이 아니라 계속 만들고 있는 프로젝트입니다

이 프로젝트에서 남은 것

모르는 언어로도 시작할 수 있습니다

Go를 몰랐고 Win32 API도 처음이었지만, 무엇을 만들지가 분명하면 시작할 수 있었습니다. AI는 문법과 API 호출을 메워줬고, 무엇이 잘못됐는지 찾는 일은 그대로 제 몫이었습니다.

테스트할 수 없는 것을 테스트 가능하게 만드는 일

실제 게임에서만 재현되는 상황을 매번 확인할 수 없어 시뮬레이터를 만들었습니다. 검증 환경을 먼저 만드는 습관은 Emour에서 평가 체계를 먼저 설계한 것과 같은 판단입니다.

안전한 쪽을 고르는 것도 설계입니다

인젝션이 더 쉽고 정확했지만 외부 읽기를 골랐습니다. Blind Dating에서 GPU 서버에 자격증명을 두지 않으려고 일부러 느린 경로를 택한 것과 같은 종류의 결정입니다.
